# nostr-leaderboard-scanner

The phone scanner for [sm64-nostr](https://github.com/wScottSh/sm64-nostr) cabinets. It feeds
[nostr-leaderboard](https://github.com/wScottSh/nostr-leaderboard).

Grab a star on the cabinet and the N64 shows a signed run as a QR code (or several cycling QR codes). Each
QR is a URL: `<BASE>#<SEQ>/<TOTAL>/<PAYLOAD>`. Build the ROM with `PIPELINE_URL_BASE` pointed at this site, and
the phone's stock camera opens the page straight from the QR:

1. **One frame:** the opened URL is the whole event. No camera permission, no app.
2. **Several frames:** the page opens the camera and collects the rest, in any order (ADR-0006).
3. It decodes the packed format-v3 bytes into the kind-8064 event (the **Run**) and checks it against the
   same rules nostr-leaderboard uses (NIP-01 id, BIP-340 signature, format-v3 shape).
4. The Submit screen asks who is claiming the Run: a name (the page makes a key and remembers it) or a pasted
   `nsec`. Nothing is published before **Submit**.
5. Submit signs a **Claim** that pairs the Run with the player's key, publishes the kind-0 name (generated keys
   only), the Run, and the Claim to the leaderboard's relays, and stamps the Claim with OpenTimestamps. The
   pending proof goes to the relays too (an `ots-pending` event). Each relay's answer is shown, failures can be
   retried, and **My claims** keeps every Claim on the phone.
6. A few seconds after Submit the page says **"Done. You can close this page."** The player's part ends
   there: the [finalizer](#finalizer) reads the pending proof from the relays and publishes the finished
   Bitcoin proof (NIP-03 kind 1040) a few hours later.

The page is a static site. The finalizer is a small job that anyone can run.

**The Run is never signed, built, or modified here.** Every signed Run value comes verbatim off the wire, and `id`
is the only derived value. All signing lives in `src/sign.js`, which signs only the player's own events (kind 0,
the Claim, the ots-pending proof) and the finalizer's (ots-pending, NIP-03 proof), and refuses any template the
leaderboard could take for a Run. Tests enforce this: only `sign.js` in `src/` and `finalizer/` touches the
signing API, the signer throws on a Run-shaped template, and the Run Submit sends is byte-identical to the decoded
one. The local signature check is informational and never blocks Submit (sm64-nostr's handoff spec). Relays and
the leaderboard verify downstream.

The key is kept in `localStorage`, so the page needs its own origin.

## Point a cabinet at it

```powershell
# in sm64-nostr (the URL is baked into every QR frame, emitted verbatim)
make PIPELINE_URL_BASE="https://wscottsh.github.io/nostr-leaderboard-scanner/" ...
```

The scanner ignores the host part: a frame decodes the same no matter which base URL wraps it.

## Contracts it depends on

| From | What | Where |
|---|---|---|
| sm64-nostr | base32/fragment/URL constants, format descriptor, `kind`, `ag-lb` tag | `src/generated/transport_contract.js`, generated by sm64-nostr's `tools/gen_transport_contract_js.py` (`npm run sync-contract`; `SM64_NOSTR=<path>` if it's not at `../sm64-nostr`). Committed so CI builds without the ROM repo. |
| sm64-nostr | real cabinet frames | `test/fixtures/multiframe_fixture.json`, copied from `reader/test/fixtures/` |
| nostr-leaderboard | relay list | `src/relay.js` `RELAYS` = leaderboard `DEFAULT_RELAYS` |
| Nostr indexers | kind-0 lookups for a pasted key; a generated key's kind-0 also goes here | `src/relay.js` `INDEXERS` = `wss://purplepag.es`, `wss://user.kindpag.es` |
| nostr-leaderboard | Claim (it ranks Claims, not built here) | kind 8064, `created_at` = Submit time, content `""`, tags `["t","ag-lb"]`, `["t","claim"]`, `["e",<run id>,<RELAYS[0]>,<run pubkey>]`, `["p",<run pubkey>]`, `["sig",<run sig>]`. Never `t=sm64` or `n`. `src/claim.js` |
| nostr-leaderboard | pending timestamp proof | kind 8064, tags exactly `["t","ag-lb"]`, `["t","ots-pending"]`, `["e",<claim id>]`, content = base64 `.ots` stamping the Claim id. Signed by the claimer at Submit, or by the finalizer when no calendar answered the page. Lets anyone finish the proof. `src/ots.js` |
| NIP-03 | finished timestamp proof | kind 1040, tags `["e",<claim id>,<RELAYS[0]>]`, `["k","8064"]`, content = base64 `.ots` pruned to its Bitcoin attestations (every calendar's, not one), signed by the finalizer's key. Published when every calendar in the Claim's pending proofs attests in Bitcoin, or when the Claim is over 12 h old and at least one does. `src/finalize.js` |
| OpenTimestamps | calendars | `src/ots.js` `CALENDARS` = alice, bob, finney (all three send CORS). `.ots` format as python-opentimestamps writes it |
| nostr-leaderboard | acceptance rules | `src/verify.js` mirrors its `verify.js` + `model.js` `parseRun` |
| nostr-leaderboard | star names, time format | `src/stars.js`, copied from its `src/stars.js` |
| nostr-leaderboard | deep links | `src/links.js`, matching its `#/c/<pubkey>/<name>/<course>-<keyId>` routes |

If any of these change upstream, update them here. The fixture's decoded event is byte-identical to
nostr-leaderboard's `test/fixtures/cabinet_event.json`, and the tests assert that.

## Finalizer

`finalizer/run.mjs` finishes the timestamps the phones start, so a player can walk away at Submit. Each run
is one stateless pass over the leaderboard relays (`RELAYS`); the relays are its only state.

1. It reads the last 7 days of Claims and `ots-pending` events and the last 8 days of kind-1040 proofs
   (by `#k`, and by `#e` for relays that don't index `#k`), plus the Runs of Claims that have no proof yet.
   If any read gets no EOSE from any relay, it logs `abort:` and publishes nothing that pass.
2. It drops any event with a bad id or signature, a tag shape other than the ones in the table above, or a
   proof that doesn't stamp the Claim it names.
3. For each Claim (`src/finalize.js`):
   - A Bitcoin-attested 1040 signed by this finalizer's own key exists: nothing to do. Other keys' 1040s
     don't count, because the finalizer can't check their Bitcoin block headers.
   - It has `ots-pending` proofs: merge them, ask their calendars for the Bitcoin path, and publish the 1040
     once ready (see the table).
   - It has no proof, is over 10 minutes old (the page closed before stamping), and the Run it names is on
     the relays and passes `checkRun`: stamp it and publish an `ots-pending`. At most 20 a pass, oldest
     first; the rest wait for the next pass.
4. It logs `expiring` for each Claim over 6 days old with no 1040 of its own; at 7 days it leaves the
   reads.

A second run right after the first publishes nothing.

Anyone can run it, from a clone:

```
npm install
node finalizer/run.mjs --dry-run   # print each decision; publish, stamp, and write nothing
node finalizer/run.mjs             # do it
```

`FINALIZER_KEY_FILE` names the hex secret key that signs its events. The default is `./finalizer.key`; the
file is created (mode 0600) when missing. `FINALIZER_RELAYS` and `FINALIZER_CALENDARS` replace the lists for
tests only. It logs one line per action and exits 0 even when some relays fail.

qrgo.fyi runs it every 5 minutes from `deploy/qrgo-finalizer.timer`, as one bundled file
(`npm run build:finalizer`).

## Develop

```
npm install
npm test        # decode, collector, verify, identity, signer, Claim planner, relays (fake socket), OTS,
                # finalizer (pure core, then the real CLI against a local relay and fake calendars)
npm run e2e     # Submit in headless Chromium against local relays and a fake OTS calendar, close the page
                # at Done, then run the finalizer and check the 1040
npm run dev     # http://localhost:8065  (camera needs https or localhost)
npm run build   # -> dist/
```

To test on a real phone you need HTTPS: deploy, or tunnel the dev server.

`SCANNER_RELAYS`, `SCANNER_INDEXERS` (comma-separated `ws://` URLs) and `SCANNER_CALENDARS` (`http://` URLs)
replace those lists at build time. They exist for local end-to-end runs; the lists never come from the URL.
`npm run e2e` uses them, then rebuilds `dist/` with the real lists.

## Deploy

`.github/workflows/pages.yml` tests, builds, and publishes `dist/` to GitHub Pages on every push to `master`.
One-time setup: repo Settings → Pages → Source = **GitHub Actions**.

`deploy/deploy.sh` ships the page to qrgo.fyi (nginx on the droplet), then the bundled finalizer to
`/opt/qrgo-finalizer` with its systemd service and timer, which it installs when missing or changed.
